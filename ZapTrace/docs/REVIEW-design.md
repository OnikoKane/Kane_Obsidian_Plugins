# ZapTrace 首版设计审查（REVIEW-design）

- 审查对象：`docs/DESIGN.md` v0.1（2026-11-02 设计基线，920 行）
- 审查人：独立验收成员（reviewer）
- 审查方式：逐条通读 + 对照 `_system/review-rules.md` + 用脚本实跑附录 B 全量评分/日期向量 + 抽查幕布规范落地值
- 本文件只做审查与建议，不改 `DESIGN.md`、不改实现。

---

## 0. 总体结论（TL;DR）

**判定：CONDITIONAL GO —— 设计质量高、边界克制，可以有条件进入开发；但开发前必须先关闭 4 个硬伤（H1–H4），并补齐测试/构建/解析器三份契约，否则会造成状态错挂与返工。**

- 设计优点：铁律「Markdown 只读、状态只在 data.json」清晰可执行；四档转移表+日期计算是**确定且可单测**的（我实跑附录 B 12 条 + 5 个日期边界，全部通过）；Live Preview 降级交代诚实；幕布令牌引用了真实规范文件且取值对得上。
- 主要风险集中在两处：**（A）ID/索引的去重与顺序假设**（同文重复题、手写重复 id、文件枚举顺序）会静默丢卡或错挂复习状态；**（B）题块「头部 vs 正文」边界与评分门禁**在实现字面下会产生歧义或越界评分。
- 建议：先关 H1–H4（约半天设计修订），再按 §13.1 的 M1–M5 开工；同时把 §3.1/§6.1 的解析与索引契约写成伪代码，作为开发与验收的共同基准。

## 1. 逐项审查（PASS / CONCERN / FAIL + 修正建议）

### R1 题块语法：能否安全表达多行 Markdown/LaTeX —— **CONCERN**

**做得好**
- 用围栏代码块 + 固定分节（`### 题干/答案/个人笔记/AI 笔记`）承载，节内先纯文本解析再交给 `MarkdownRenderer.render`，`$…$`/`$$…$$`/列表/表格都能渲染（§3.1、§5.1）——方向正确。
- 4 反引号外层套 3 反引号的 CommonMark 规则，能解决「答案里含代码块」，是对的做法（§3.1、§3.5）。
- 不用 YAML、不用行内 `{{}}` 的理由（数学里 `:`/`|`/`\`/花括号多）成立，取舍透明（§3.6）。

**问题（会导致返工）**
1. **头部/正文边界歧义（H3）**：§3.2 规定「以一行单独的 `---` 结束头部；无头部时第一行直接是正文」。但**题干里出现 Markdown 水平线 `---` 非常常见**。按字面实现，一条无头部、题干含 `---` 的题卡，会把 `---` 之前的题干误判为「头部区」，非 `key:` 行被归入 `extra` 后丢弃 → **静默吞掉半道题干**。这是语法「不安全表达多行正文」的直接反例。
2. **未知键/非键行未定义**：§3.2「其他未知键保留进 extra」，但没有规定「不含冒号的行出现在头部区」时怎么办（报错？保留？结束头部？），实现只能猜。
3. **分节标题匹配过严**：§3.3 只认 `### 题干` 等固定串。`###题干`（无空格）、`### 答案 `（尾随空格）、整体缩进的题块（行首多空格）都会匹配失败而静默降级。
4. **缺 `### 题干` 但有其他分节** 未定义（§3.5 只写了「缺题干且无分节」）。

**修正建议**
- 头部识别改为**先看首行**：仅当第一个非空行匹配 `^[A-Za-z][A-Za-z0-9_-]*\s*:` 时，才进入「头部态」，并在头部态内寻找第一条独立 `---` 作为终止；否则**整段从第一行就是正文**（不做任何头部剥离）。这样题干里的 `---` 永远安全。
- 头部态内遇到非 `key:` 行：**立即结束头部、该行起全部归正文**（或至少原样保留，绝不丢弃）。
- 分节标题用宽松正则：`^#{3,}\s*(题干|答案|个人笔记|AI\s*笔记)\s*$`，并允许行首缩进（先按代码块公共缩进做 dedent）。
- 明确「有 `### 答案` 但无 `### 题干`」= 语法错误（题干显示「缺少题干分节」），并给出行号。
- 在 §3.5 补一张**解析器真值表**（见 §4 建议的 Appendix C）。

### R2 稳定 ID：同文重复题 / 移动行 —— **FAIL**

这是本设计**最硬的缺陷**，会直接导致「丢卡」或「复习状态挂错题」，必须在开发前修掉。

**做得好**
- 手写 `id` 优先、自动 `auto:`+SHA-1(规范化题干) 前 12 位；改答案/笔记/标签不改 qid，改题干才换 ID 且旧记录 `orphaned` 保留不删（§4.1/§4.4）——这套「内容寻址 + 孤儿保留」方向正确。
- 规范化只做 NFC + 空白归一，不折叠大小写，尊重数学符号大小写差异（§4.2）——正确。

**问题**
1. **同文重复题必然碰撞（H1）**：自动 ID 只由题干决定。若同一道题在库里出现两次（复习卷重复、多本笔记抄同一题极常见），两卡得到**同一个 qid**。而 §6.1 索引是 `Map<qid, Card>` —— **后写覆盖先写，题集里直接少一张卡**；同时两张卡共用一份 `star/due/step`，评分互相污染。§3.5 的「`id` 重复」只覆盖**手写 id**，完全没覆盖**自动 hash 重复**。
2. **手写重复 id 的「先出现者」依赖枚举顺序（H2）**：§3.5 说重复 id「保留先出现者，后来者派生 `qid-2`」。但「先出现」取决于 `getMarkdownFiles()` 的枚举顺序与文件内块顺序；**重命名、移动文件、增删文件都可能翻转谁先出现** → 同一份复习状态在两道题之间来回错挂。且「qid-2」命名规则不明确（第 3 个重复叫 qid-3？与 auto 哈希如何拼接？）。
3. 移动行本身**不**影响自动 ID（只依赖题干文本，不含行号），这点没问题；**真正脆弱的是「谁先出现」这一步**（同问题 2）。

**修正建议（择一或组合）**
- **索引键与状态键分离**：内存索引用 `${相对路径}#${块序号}` 作唯一键，`qid` 只作为 `data.json` 的状态 key；渲染/筛选/练习都走「卡片实例」，状态用 qid 关联。这样同文重复题是两张不同的卡，不会互相覆盖。
- **自动 ID 加确定性消歧**：当 `hash(stem)` 命中第二张卡时，追加确定性后缀 `-` + `hash(相对路径 + 块偏移)` 的前 6 位；并保证**不依赖枚举顺序**（用路径+字节偏移排序后再分配）。
- **手写重复 id**：不要「先到先得」。改为「重复即冲突」：所有重复者一律降级为 auto-id 并在题集标 `!重复ID`，或在 UI 强制用户改名；若保留迁移能力，用 (路径, 偏移) 的确定性排序选「规范 id」持有者，其余降级。
- §3.5 增补一行：**自动 hash 重复**的处理与手写重复同等对待。
- 加单元测试：同文两道题 → 两个不同 qid、各自独立状态；重复手写 id → 状态不随文件重排而迁移。

### R3 原 Markdown 与 data.json 边界 —— **PASS**

**做得好**
- 「题干/答案/笔记/标签只存在于 Markdown；收藏/评分/到期只存在于 `data.json`」一条铁律贯穿全文（§0、§4.3、§9.4）。
- 写入面收敛到两处：用户显式触发的「插入题卡模板」，以及 `saveData`/迁移备份写插件目录的 `data.json`（§4.3 表、§9.1）。**不会往 `.md` 追加隐藏注释/行尾标记**，git 历史干净——这点非常对。
- 派生 vs 持久分得清：卡片正文永远实时解析，`data.json` 丢失可重新索引重建题目（§9.4）。
- data.json 路径规范（`plugins/zaptrace/data.json` 经 `saveData`），迁移前备份、未知字段保留、降级只读模式（§9.5）——稳。

**建议（不阻塞，写进文档即可）**
- **写放大**：§9.3 说 `subject/tags/source` 每次索引随卡片刷新。意味着「每改一次任意笔记」都可能触发对 `data.json` 的整盘写。建议明确：**仅当这些缓存值实际变化时才落盘**，并做 300–500ms 防抖，避免频繁 IO。
- **原始 HTML 信任模型**：§5.4 只承诺「不拼 innerHTML」，但 `MarkdownRenderer.render` 对题卡里的**原始 HTML** 是否消毒取决于 Obsidian 版本。建议明确「题卡内容视为作者可信输入；如需强隔离，走 DOMPurify 或禁用原始 HTML」。
- **多设备**：§13.2 已列为非目标并给风险提示，合理；建议在 data.json 头加 `deviceInstanceId` 便于日后冲突诊断（v0.2）。

### R4 答案未展开不能评分 —— **CONCERN**

**做得好**
- §7.1 第 2 步明确「只渲染题干；答案与笔记 DOM 不注入，防偷看」；§14.5 有「开发者工具确认答案 DOM 未注入」的验收项——把「先作答」落在 **DOM 不预渲染**上，而不是靠文案提醒，很扎实。
- 答案懒渲染（首次展开才 `MarkdownRenderer.render`）+ 折叠态不建答案 DOM（§5.3），既防偷看又省性能。

**问题（H4）**
- §10.6 / §11 规定「快捷键 `1/2/3/4` 直接评分」。但**没有把评分快捷键/评分条的可用性显式绑定到 `revealed === true`**。若全局注册了 1–4 键盘处理，用户在只看题干、还没点「显示答案」时按 1–4 就可能直接写入评分 → **违反「答案未展开不能评分」这条硬要求**。这属于交互边界漏洞，实现按字面很容易踩。

**修正建议**
- 评分状态机显式三态：`viewing(未揭晓) → revealed(已揭晓) → rated`。`viewing` 态：**评分条不渲染进 DOM、1–4 键盘处理器 early-return、无任何写 `data.json` 路径**；`aria-disabled` 也不够，要真不渲染/不响应。
- 键盘处理只在 `revealed && !rated` 时激活；`Esc` 在 `viewing` 态回到题集。
- 加验收用例：未揭晓时连按 1–4，断言 `data.json` 字节不变、无 `reviewLog` 新增。

### R5 四档复习日期规则 —— **PASS**

**我实测过，确定且可测。** 用脚本按 §8.2 公式重算附录 B 全部 12 条向量与 5 个日期边界：

- 12 条评分向量 **全部 OK**（含 step=-1/0/1/2/3/4 × again/hard/good/easy 的关键组合）。
- 公式与表格等价：`again→(-1,1d)`；`hard→max(-1,step-1)`；`good→min(4,step+1)`；`easy→min(4,step+2)`；`days=STEP_DAYS[max(step',0)]`，`STEP_DAYS=[1,3,7,15,30]`，逐格一致。
- 日期边界 **全部 OK**：`2026-01-31+3=2026-02-03`、`2026-12-30+7=2027-01-06`、`2028-02-28+1=2028-02-29`、`2027-02-28+1=2027-03-01`、`2026-11-02+30=2026-12-02`。
- 「again 永远 1 天、不会当天再到期」避免死循环，考虑周到；用 `moment.add(days,'day')` 处理跨月/闰年/夏令时、明令禁止手写 `+86400000`，正确。

**建议（防御性，补文档即可）**
- **step 越界钳制**：`data.json` 被手改或旧版本残留可能出现 `step=5 / -2`，此时 `STEP_DAYS[max(step,0)]` 可能越界/取 `undefined` → 生成 `NaN` 日期。加载时统一 `step = clamp(step, -1, 4)`。
- **「今天到期」vs「已到期」定义**：§2.3/§7.2 用 `due <= 今天` 都算到期；但 §6.2 时间筛选把「今天到期 / 已到期」并列。请明确：`今天到期 = (due == today)`、`已到期 = (due < today)`，避免筛选与队列口径不一致。
- **每日上限与系统规则不一致**：§12.2 `dailyReviewLimit` 默认 **20**，而 `_system/review-rules.md` §4 每日上限 **8 条**。§8.5 只声称「间隔同构」，未提上限差异——建议注明「ZapTrace 为独立插件，上限默认 20，不复用学习系统的 8 条」，避免读者误以为一致。

### R6 首版是否过度设计 —— **CONCERN**

**客观评价**：设计本身克制（明确 8 项非目标、拒绝统计/AI/云同步），但 **v0.1 交付清单（§13.1）仍偏重**：三栏工作台 + 全库索引 + 多维筛选 + 四档评分 + 复习队列 + 时间记录 + schema 迁移脚手架 + 移动端单栏 + 完整 ARIA + 500 卡 <1.5s 性能目标，一次全落地对单个开发者风险偏高，容易「每项 80%」而核心闭环不稳。

**建议裁剪到「首版最小可用闭环」（与本次验收重点对齐）**
- **必须**：解析器 + 阅读视图卡片（Star/答案折叠/笔记折叠）+ 题集基础筛选（科目标签/时间/搜索）+ 练习闭环（未揭晓→揭晓→四档→写状态）+ 四档转移表与日期 + `data.json`（schemaVersion=1 + 安全模式）+ 幕布令牌 + reduced-motion + 构建/核心测试。
- **可延后 v0.1.x**：移动端单栏与底部 Tab（先保证桌面可用）、时间记录 7 天展开、`snooze`、PDF 来源置灰筛选、token 倒排索引（§6.1 与 §6.2 自相矛盾：既然「首版子串即可」，就不必建 token 倒排）、`schemaVersion` 多级迁移（首版只做「版本不符→只读+提示」即可）。
- 里程碑 §13.3 已分 M1–M5，建议在 M1 里明确「解析器 + 评分函数 + data.json 三件套先跑通单测」，其余按 M2–M5 递增，避免大爆炸式集成。

> 结论：不是「设计过度」，而是「**首版范围承诺过大**」。把 §13.1 收敛为上述「必须」清单，即可显著降返工风险。

### R7 Obsidian 阅读/实时预览降级是否诚实 —— **PASS**

- 阅读视图用稳定公开 API `registerMarkdownCodeBlockProcessor("zaptrace", handler)` + `MarkdownRenderer.render(app, text, el, sourcePath, component)`（现代签名，正确）；理由「阅读视图静态、DOM 不被编辑器高频重建、点击态不闪回」成立（§5.1）。
- Live Preview 明确承认「光标进入代码块会切回源码、重渲染可能吞点击态」，首版降级为**只读缩略卡 + 在阅读视图/工作台打开**，并说清「不承诺 LP 内完成评分」（§5.2）——**诚实、无过度承诺**。
- 兜底（processor 不生效时原代码块仍是合法 Markdown）也交代了（§5.3）。

**建议（小）**
- 各 Obsidian 版本对 LP 里代码块处理器的调用行为有差异。建议**运行时 feature-detect**（如检测当前视图模式），并在真机矩阵（1.x 若干版本、桌面+移动）各点一遍，避免「LP 里既渲染缩略卡又保留源码」双份。
- `minAppVersion` 需在 manifest 明确（如 `1.5.0`），并在设计里注明验证过的 Obsidian 版本。

### R8 幕布风 / 可访问性 / 测试是否可执行 —— **CONCERN**

**做得好**
- 幕布令牌与数值我对照了 `C:\Users\10784\Desktop\幕布UI设计规范.md`：`#5854d4` 只用于控件、`6px 圆点 + 6px spread = 18px 圆盘`、入场 60–160ms、正文 16px/2.1——**逐项对得上**，可执行。
- §10.8 直接给了 `prefers-reduced-motion: reduce` 的 CSS 片段，reduced-motion 要求可落地。
- §11 键盘与 ARIA 覆盖面广，§14 验收清单可勾选。

**问题（需补，否则验收无抓手）**
1. **a11y 角色用法有冲突**：§11 让题集列表 `role="listbox"` + `option`，但 §6.3 每行内含可点的 `[★]` Star 按钮 —— **listbox 的 option 里嵌 button 是无效语义**，读屏不会正确暴露。建议改用 `role="list"` + 每行 `button`（打开）与兄弟 `button`（Star），或 `role="grid"`；若坚持 listbox，则 Star 必须移出 option。
2. **`aria-controls` 需要稳定唯一 id**：§10.2 折块用 `aria-controls`，而 qid 含 `.`/`:`，直接当 DOM id/`querySelector` 会踩选择器转义坑。建议 DOM id 用自增序号或 `zt-c-<hash>`，qid 只存 `data-qid`。
